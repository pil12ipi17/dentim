# Feature Specification: Android Karaoke MVP

**Feature Branch**: `001-android-karaoke-mvp`  
**Created**: 2025-11-11  
**Status**: Draft  
**Input**: User description: "нужно сделать mvp приложение на андроид на котлине - суть приложения онлайн караоке клиент-серверная архитектура Клиент (front-end) — Android-приложение (на Kotlin, Flutter или Unity). Оно показывает интерфейс, позволяет выбрать песню, следит за прогрессом. Сервер (back-end) — Python-приложение с ИИ-моделью (например, Demucs или Spleeter). Оно принимает аудиофайл, вырезает вокал и возвращает минусовку обратно."

## Clarifications

### Session 2025-11-11

- Q: Как обрабатывать конфиденциальность пользовательских аудиофайлов на сервере? → A: Файлы обрабатываются временно и удаляются с сервера сразу после обработки
- Q: Как обрабатывать множественные файлы одновременно? → A: Блокировать интерфейс до завершения текущей обработки
- Q: Как восстанавливаться после сетевых ошибок? → A: Автоматически повторять загрузку с экспоненциальной задержкой (3 попытки)
- Q: Какое качество аудио для выходных минусовок? → A: Позволить пользователю выбрать качество (высокое/среднее/экономное)
- Q: Максимальный тайм-аут для запроса обработки? → A: 30 секунд максимум

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Voice Separation Processing (Priority: P1)

Пользователь загружает аудиофайл песни в Android приложение, система обрабатывает его на сервере с помощью ИИ-модели для удаления вокала и возвращает инструментальную минусовку готовую для караоке.

**Why this priority**: Это базовая функциональность приложения - без возможности создания минусовок само караоке приложение теряет смысл. Эта история покрывает весь основной pipeline от клиента до сервера.

**Independent Test**: Можно полностью протестировать загрузив один аудиофайл через Android приложение и получив обратно обработанную минусовку для воспроизведения.

**Acceptance Scenarios**:

1. **Given** пользователь имеет Android приложение и аудиофайл песни, **When** пользователь выбирает файл и запускает обработку, **Then** система показывает прогресс загрузки и обработки
2. **Given** аудиофайл загружен на сервер, **When** ИИ-модель обрабатывает файл, **Then** система возвращает минусовку без вокала в приложение
3. **Given** минусовка готова, **When** пользователь нажимает воспроизведение, **Then** звучит инструментальная версия песни

---

### User Story 2 - Song Selection Interface (Priority: P2)

Пользователь видит удобный интерфейс для выбора и управления песнями в Android приложении, включая список доступных треков и возможность добавления новых.

**Why this priority**: Хотя можно начать с простой загрузки файлов, удобный интерфейс критичен для пользовательского опыта и делает приложение пригодным для регулярного использования.

**Independent Test**: Можно протестировать навигацию по интерфейсу, выбор песен и управление библиотекой без необходимости полной обработки аудио.

**Acceptance Scenarios**:

1. **Given** пользователь открывает приложение, **When** он видит главный экран, **Then** отображается список доступных песен и кнопка добавления новой
2. **Given** пользователь хочет добавить новую песню, **When** он нажимает кнопку добавления, **Then** открывается файловый браузер для выбора аудиофайла
3. **Given** пользователь выбрал песню из списка, **When** он нажимает на нее, **Then** запускается экран с опциями обработки (включая выбор качества) и караоке

---

### User Story 3 - Processing Progress Monitoring (Priority: P3)

Пользователь видит детальный прогресс обработки аудиофайла с возможностью отмены операции и получает уведомления о завершении.

**Why this priority**: Улучшает пользовательский опыт, но не критично для базовой функциональности. Можно начать с простого индикатора загрузки.

**Independent Test**: Можно протестировать отображение прогресса и уведомления независимо от качества обработки аудио.

**Acceptance Scenarios**:

1. **Given** обработка аудиофайла начата, **When** пользователь находится в приложении, **Then** отображается прогресс-бар с процентами выполнения
2. **Given** обработка занимает много времени, **When** пользователь нажимает кнопку отмены, **Then** операция прерывается и пользователь возвращается к списку песен
3. **Given** обработка завершена успешно, **When** пользователь не находится в приложении, **Then** приходит push-уведомление о готовности минусовки

---

### User Story 4 - Future AI Text Synchronization (Priority: P4)

В будущих версиях система сможет автоматически находить текст песни через Whisper или позволять пользователю вводить текст вручную, синхронизируя его с аудио для создания полноценного караоке-видео.

**Why this priority**: Это расширенная функциональность для будущих версий, не требуется для MVP.

**Independent Test**: На данном этапе не тестируется, служит как план развития.

**Acceptance Scenarios**:

1. **Given** минусовка готова, **When** пользователь выбирает опцию добавления текста, **Then** система предлагает автопоиск через ИИ или ручной ввод
2. **Given** текст песни найден или введен, **When** пользователь запускает синхронизацию, **Then** создается караоке-видео с подсветкой текста в такт музыке

---

### Edge Cases

- Что происходит когда аудиофайл слишком большой (>100MB) или в неподдерживаемом формате?
- Как система обрабатывает инструментальные композиции без вокала?
- Что делать при сетевых ошибках во время загрузки или обработки?
- Как обрабатываются файлы с очень тихим или искаженным вокалом?
- Что происходит при одновременной обработке нескольких файлов? (Решено: интерфейс блокирует новые загрузки)
- Как обрабатываются сетевые ошибки при прерывании соединения в процессе загрузки? (Решено: автоповтор с задержкой)

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Android приложение ДОЛЖНО позволять пользователям выбирать аудиофайлы из устройства для обработки
- **FR-002**: Система ДОЛЖНА поддерживать популярные аудиоформаты (MP3, WAV, FLAC, M4A)
- **FR-003**: Клиент ДОЛЖЕН загружать выбранный аудиофайл на сервер для обработки
- **FR-004**: Сервер ДОЛЖЕН использовать ИИ-модели для разделения аудио и удаления вокала (Demucs, Spleeter или аналоги)
- **FR-005**: Система ДОЛЖНА возвращать обработанную инструментальную минусовку обратно в Android приложение
- **FR-006**: Приложение ДОЛЖНО воспроизводить как оригинальную песню, так и созданную минусовку
- **FR-007**: Интерфейс ДОЛЖЕН показывать прогресс загрузки и обработки файла в реальном времени
- **FR-008**: Пользователи ДОЛЖНЫ иметь возможность отменить операцию обработки во время выполнения
- **FR-009**: Система ДОЛЖНА сохранять обработанные минусовки локально на устройстве для повторного использования
- **FR-010**: Приложение ДОЛЖНО предоставлять список ранее обработанных песен с возможностью их воспроизведения
- **FR-011**: Сервер ДОЛЖЕН обрабатывать ошибки и возвращать понятные сообщения об ошибках клиенту
- **FR-012**: Система ДОЛЖНА ограничивать размер загружаемых файлов максимум 100MB для поддержки длинных композиций и файлов без потерь при умеренной нагрузке на сервер
- **FR-013**: Сервер ДОЛЖЕН удалять все пользовательские аудиофайлы немедленно после завершения обработки для обеспечения конфиденциальности
- **FR-014**: Интерфейс ДОЛЖЕН блокировать возможность загрузки новых файлов до завершения текущей обработки для упрощения управления ресурсами
- **FR-015**: Приложение ДОЛЖНО автоматически повторять загрузку при сетевых ошибках максимум 3 раза с экспоненциальной задержкой перед уведомлением пользователя о неудаче
- **FR-016**: Система ДОЛЖНА предоставлять пользователю выбор качества выходной минусовки: высокое (44.1kHz/16-bit), среднее (22kHz/16-bit), экономное (22kHz/8-bit)
- **FR-017**: Сервер ДОЛЖЕН устанавливать максимальный тайм-аут 30 секунд для ответа на запрос начала обработки

### Key Entities

- **Песня (Song)**: Представляет аудиофайл с метаданными (название, исполнитель, длительность, путь к файлу)
- **Минусовка (Instrumental)**: Обработанная версия песни без вокала, связанная с оригинальной песней
- **Задача обработки (Processing Task)**: Представляет операцию по обработке аудиофайла с статусом (в очереди, обрабатывается, завершена, ошибка)

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Пользователи могут успешно загрузить и обработать аудиофайл размером до 50MB за время менее 5 минут
- **SC-002**: Качество разделения вокала достигает приемлемого уровня для караоке (субъективная оценка пользователя "хорошо" или выше в 80% случаев)
- **SC-003**: Система поддерживает одновременную обработку минимум 3 файлов без критического снижения производительности
- **SC-004**: Пользователи могут найти и воспроизвести ранее обработанную минусовку за время менее 30 секунд
- **SC-005**: Интерфейс позволяет пользователю понять текущий статус обработки файла в течение 2 секунд после открытия приложения
- **SC-006**: Система корректно обрабатывает и сообщает об ошибках в 95% случаев некорректных входных данных
- **SC-007**: Время отклика сервера на запрос обработки составляет менее 10 секунд (время начала обработки, не завершения) с максимальным тайм-аутом 30 секунд
- **SC-008**: Пользователи могут отменить операцию обработки и вернуться к нормальной работе за время менее 5 секунд

### Assumptions

- Пользователи имеют стабильное интернет-соединение для загрузки файлов на сервер
- Большинство аудиофайлов будут в стандартном качестве (44.1kHz, 16-bit) и стандартной длительности (3-6 минут)
- Пользователи готовы ждать несколько минут для качественной обработки ИИ
- Начальная версия не требует системы аутентификации пользователей
- Локальное хранение обработанных файлов на устройстве пользователя приемлемо
- ИИ-модели будут развернуты на выделенном сервере с достаточными вычислительными ресурсами
